3  Architecture

Sarathy is one asyncio process. Everything that can talk to the outside world — five channel adapters, the agent loop, the session store, the scheduler, the background reviewer, the heartbeat, and an embedded web server — runs inside a single event loop started by run_gateway() in sarathy/gateway/run.py.

That single decision is the source of most of the system’s simplicity: no IPC, no serialisation at the seams, no distributed tracing, and a data flow you can read end to end in one function.

3.1 The system map

Read the picture in three moves:

  1. Adapters translate, they do not think. Every channel adapter turns its platform’s events into InboundMessage and its replies into OutboundMessage, and publishes them on one shared MessageBus. The agent never learns whether a turn came from a chat app, a browser tab, or a scheduled job.
  2. The loop owns the turn. AgentLoop is the only component that calls the model, runs tools, or writes to a session.
  3. State lives in files. Sessions, memory, skills and cron definitions are files in the workspace. SQLite appears in exactly three places, each of which needs a real query surface (see Chapter 3).

3.2 The gateway process

run_gateway() is a straight-line assembly function, which is deliberate: you can read it top to bottom and know the whole object graph. In order it constructs:

Step Object File Why it is created here
1 MessageBus bus/queue.py Two asyncio.Queues, nothing else
2 RuntimeProvider providers/manager.py Owns the live provider + model + sampling params
3 SessionManager session/manager.py JSONL store, LRU cache, SQLite index
4 CronService cron/service.py Scheduler over a single JSON job file
5 AgentLoop agent/loop.py The turn engine; receives the bus, provider, sessions, tools config
6 BackgroundReviewer session/review.py Idle-time learning, attached to the loop
7 SkillManager + CommandManager agent/skills.py, core/commands.py Skills become slash commands
8 ChannelManager channels/manager.py Instantiates and starts the enabled adapters
9 HeartbeatService heartbeat/service.py Periodic wake-up, bound to the agent
10 cron/heartbeat callbacks wired in run.py Bridge from timers into the agent loop

Then it does the only interesting thing structurally:

await asyncio.gather(
    agent.run(),        # consumes the inbound queue forever
    channels_task,      # starts adapters + outbound dispatcher forever
)

agent.run() and the channel set are the two long-lived coroutines. Everything else — cron ticks, heartbeat ticks, background review, MCP connection setup — is a task spawned from one of them. Shutdown is symmetric: MCP exit stack closed, heartbeat stopped, cron stopped, agent stopped, channels stopped.

3.2.1 Process lifecycle

The daemon itself is managed by a thin wrapper, sarathy/gateway/manager.py: start spawns python -m sarathy.gateway.run --port N with start_new_session=True, writes the child’s PID to a file, and lets the child redirect its output to a timestamped log. stop sends SIGTERM. status probes the PID with signal 0 and clears the file if the process is gone. logs tails the newest log file, with --follow for tail -f behaviour.

Note what is not here: no supervisor, no service manager, no container orchestration, no PID-file locking beyond the single file. The daemon is deliberately the simplest thing that survives a terminal closing.

3.3 The message bus

Two dataclasses and two queues (sarathy/bus/events.py, sarathy/bus/queue.py):

@dataclass
class InboundMessage:
    channel: str
    sender_id: str
    chat_id: str
    content: str
    timestamp: datetime = field(default_factory=datetime.now)
    media: list[str] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)
    session_key_override: str | None = None

    @property
    def session_key(self) -> str:
        return self.session_key_override or f"{self.channel}:{self.chat_id}"

That session_key property is the load-bearing line of the whole design. Session isolation is not a policy enforced at the storage layer; it is a string computed once, at the edge, and carried by the message. Everything downstream — caching, archival, cost accounting, /stop targeting — keys off that string. If the channel layer computes the right key, the rest of the system cannot get it wrong.

metadata is the second load-bearing decision: it is the per-channel escape hatch. Message identifiers for threaded replies, image-provider role overrides, tool-hint flags, _progress markers, /btw markers, and usage-role overrides all travel as metadata rather than as new message types or new bus methods. The bus never learns a new concept.

OutboundMessage is smaller — channel, chat_id, content, reply_to, media, metadata — because the send path is genuinely uniform: look the channel up by name, call send().

3.4 A message’s journey

Four things in that diagram are worth reading twice.

Permission is checked at the edge, once. BaseChannel._handle_message calls is_allowed(sender_id) and drops the message if the sender is not on the allow-list. The agent loop never re-checks, because it cannot be reached by anything that did not pass through an adapter.

Concurrency is layered, and the order is fixed. _dispatch() acquires, in order: the global lock (which guards runtime hot-reload, config mutations and the archival sweep), then a semaphore capping concurrent sessions (maxConcurrentSessions, default 4, clamped to 1..16), then the per-session lock. The rule “never hold a session lock while acquiring the global lock” is written into the code as a comment at the point where it would be violated.

The model is called from exactly one place. _run_agent_loop() is a while iteration < max_iterations loop around a single provider.chat() call. Everything that looks like an agent loop elsewhere in the system — cron runs, heartbeat ticks, /btw side turns, subagents — re-enters this same function. That is what makes the cost ledger, the usage footer, the steer injection point and the reviewer idle-gate work without special cases.

Progress is a message, not a channel. Long turns emit intermediate OutboundMessages carrying _progress (and optionally _tool_hint) metadata. The outbound dispatcher drops them unless the channel config asks for them (sendProgress, sendToolHints). Channels that support drafts rewrite the same message over and over; channels that do not simply ignore them.

3.5 The agent loop, in detail

AgentLoop.run() is a poll loop with a one-second timeout so it can notice shutdown, plus three commands it intercepts before dispatching:

  • /stop — cancels every tracked task for that session key and every subagent spawned from it.
  • /steer — enqueues an instruction into the running session’s steer queue. The loop drains that queue at the top of every iteration, so a steer takes effect immediately after the current tool call returns, not after the whole turn. If the session is idle, the prefix is stripped and the text is dispatched as an ordinary message.
  • /btw — starts a genuinely concurrent second turn against a snapshot of the session, in its own ##btw## session, whose result is delivered when it is ready. It even saves and restores the message tool’s per-turn state so the side turn cannot pollute duplicate suppression for the main turn.

Everything else is dispatched as a task, tracked per session key, so that a slow turn in one chat never blocks another.

Inside _run_agent_loop(), per iteration, in this exact order:

  1. Drain the steer queue and append any steers as synthetic user messages.
  2. If a per-turn provider role was requested and images are present, hand the images to the provider tagged with the image role and rewrite the user message with a textual description (the “describe-then-inject” step).
  3. Call the provider, streaming if the session or channel asks for it.
  4. Record usage telemetry — always, and never fatally: a telemetry failure must not break a turn.
  5. If there are tool calls: emit a tool hint, execute each one through the registry, append the results, and loop.
  6. Otherwise stop, and let the caller apply topic markers, the usage footer and session persistence.

3.6 Tools

A tool is a dataclass-shaped ABC with four members: name, description, parameters (a JSON schema) and async execute(**kwargs) -> str (sarathy/agent/tools/base.py). The registry turns that into OpenAI-style function definitions and enforces three things before the tool body runs (sarathy/agent/tools/registry.py):

  • schema validation of the incoming parameters, with a readable error listing which parameter was wrong;
  • a uniform error string, appended with an explicit instruction to the model to analyse the failure and try a different approach rather than repeating the same call;
  • registration order stability, so the cached prompt prefix does not churn.

The default set registered at construction time is: filesystem (read, write, edit, list), shell execution, web fetch, optional web search, message send, subagent spawn, cron (only when a scheduler is wired in), memory, and skill management. MCP servers, if configured, are connected lazily on the first turn and their tools are merged into the same registry, so the agent cannot tell where a tool came from.

Workspace restriction is enforced at tool construction, not at call time: restrict_to_workspace becomes the allowed_dir passed into the filesystem tools and the working directory for the shell tool.

3.7 Sessions

SessionManager (sarathy/session/manager.py) is three cooperating things:

  • an LRU cache (OrderedDict, default 50 entries) of live Session objects, because a session is mutated in memory and flushed to disk opportunistically;
  • a JSONL file per session key, whose first line is a metadata record and whose remaining lines are messages — append-friendly, greppable, and readable by anything that speaks JSON;
  • a SQLite index (sessions/index.db) holding one row per session (key, channel, topic, timestamps, archived flag) so listing sessions is a single indexed query instead of reading every transcript.

A Session is deliberately a plain list of message dicts plus a metadata dict. get_history() slices the unconsolidated tail, aligns it to a user turn so the model never sees an orphaned tool result, and projects only the fields the API cares about. History is append-only for prompt-cache efficiency: nothing in the turn path edits or rewrites past messages.

Rotation happens in two places for two reasons. Session.add_message() rotates mid-turn when an interactive session reaches its size cap. get_or_create() rotates between turns for cron sessions, which must never rotate mid-run — see the 500-message hard lesson.

Archival writes a timestamped JSONL file into archived_sessions/, stamped archived: true only when the reviewer confirms it had no pending work for that session. Unstamped archives are re-verified once at gateway startup as crash recovery, and prune_archives() reaps old files while keeping anything still unverified, so a crash can never silently discard pending learning.

3.8 Providers and hot reload

providers/registry.py holds a frozen table of provider metadata: name, keywords, environment variable, display name, LiteLLM prefix, whether it is local, and a default API base. Four kinds are supported — three local, one “anything OpenAI-compatible”. providers/manager.py turns a config entry into a client: direct HTTP client for OpenAI-compatible endpoints (which preserves reasoning content that LiteLLM would flatten), LiteLLM otherwise.

The interesting part is RuntimeProvider. It holds the live provider and model, and it re-reads the config file when — and only when — the file’s modification time changes:

def refresh(self) -> bool:
    mtime = self._file_mtime()
    if mtime == self._mtime:
        return False
    ...

Rebuilding the client only happens if the active provider, model, temperature, max tokens or reasoning effort actually changed. A failed rebuild keeps the old provider rather than dropping to no provider at all. Every turn calls runtime.apply_to(agent) under the global lock, which is why switching models from the dashboard or the CLI takes effect on the next message without a restart — while changing gateway source still requires a restart. The distinction is drawn on purpose; see Chapter 4.

Providers also carry roles (main, local, image), resolved per turn. A cron job payload can declare that it wants the local role, and the loop swaps the provider for that turn only, restores it in a finally block, and stamps the reply so the operator can see which provider ran it.

3.9 The dashboard as a channel

The dashboard is not a separate service. DashboardChannel starts an aiohttp application inside the gateway’s own event loop (sarathy/channels/dashboard/server.py), serves the built single-page app, and exposes a REST API that operates directly on config, sessions and workspace files.

Two details are deliberate. First, the auth middleware validates pairing keys against the on-disk config on every request, so revoking a key from the CLI takes effect immediately instead of at the next restart; devices that pair successfully receive an opaque token whose hash is persisted, so a reconnect after a restart stays authenticated. Second, any config value whose key looks sensitive is replaced with a placeholder before the config document is handed back over the API, so the UI can render “set / not set” without ever receiving the value.

3.10 The backend trigger path

Added in 0.15.0, sarathy/channels/backend.py is the one adapter that is not a chat platform. It exists so that programs — not people — can start a turn. It has two independent ways in:

  • a loopback-only HTTP endpoint that accepts a signed event envelope;
  • a tailer that polls a jobs database read-only for new rows in an events table and wakes a session per job.

The security posture is conservative by construction, not by policy:

  • it refuses to start at all if no credential is configured;
  • a non-loopback bind address is forced back to loopback with a warning, so misconfiguration cannot expose it;
  • the token comparison is constant-time;
  • the jobs database is opened with SQLite’s read-only URI flag, so the tailer physically cannot write;
  • the tailer stores a high-watermark and, on first run, initialises it to the current maximum event id — history is never replayed into a session.

3.11 Where the state lives

The rule of thumb the codebase follows: if you would open it in a text editor to understand it, it is a file; if you would only ever query it, it is SQLite. Sessions and memory are files because reading a transcript is a real debugging need. The sessions index, the usage ledger and the jobs ledger are SQLite because nothing reads them by eye — they exist to answer questions, and a directory of JSONL files cannot answer “all sessions updated in the last week” without a scan.
