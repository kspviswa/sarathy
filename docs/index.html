Sarathy Engineering

Architecture, patterns and the decisions behind a local-first personal AI assistant

Published

2026-10-04

Last updated: 2026-10-04 · Status: living document · Book version: tracks release 0.15.0

Sarathy is a personal AI assistant built to run locally, on the operator’s own hardware, against local models. This book is the engineering record behind it: how the system is put together, which patterns it leans on, and why each significant decision was made the way it was.

It is written for engineers, not for users. If you want to install and run the assistant, read the project README instead. If you want to know how the thing is built and why it is built that way, you are in the right place.

0.2 House rules for this book

This book is destined for public hosting. Three rules are absolute, and they are enforced mechanically by the smoke test rather than by good intentions:

  1. No personal information. No real names — the book says “the operator”, “the author”, “the user”. No chat identifiers, no contact details, no credentials of any kind.
  2. No private paths. Everything is named relative to the repository root (sarathy/agent/loop.py) or relative to the workspace (workspace/sessions/). The machine’s home directories are never spelled out.
  3. No private content. Nothing from the operator’s actual conversations, memory store or job records is quoted. The book describes mechanisms, never payloads.

Anything added to the book has to pass python3 -m unittest discover tests -k book, which scans both the .qmd sources and the rendered .html for the patterns above. See the update workflow in doc/README.md for how to add a chapter or a log entry.

0.3 Provenance: how claims in this book are sourced

Nothing here is invented. Every factual claim traces to one of four places, and the book says which:

  • The code. Repository-relative file paths and symbols, e.g. sarathy/session/manager.py (SessionManager._should_rotate).
  • The history. Commits are referenced by their short hash and subject, e.g. 67a3176 “rotate cron sessions at the trim cap”.
  • The operator’s engineering notes. A small number of decisions are not visible in the code at all — they are operational practice (how work is delegated, how releases are tracked). Those are drawn from the author’s notes and are labelled explicitly as such, because the repository cannot corroborate them.
  • Absence of evidence. Where the repository contradicts an expectation, the book says so rather than papering over it. For example, there is no in-tree text-to-speech pipeline; see the media-handling pattern in Chapter 3.
